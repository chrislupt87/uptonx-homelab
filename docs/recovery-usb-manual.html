Recovery USB Setup

Ventoy multi-boot USB with ISOs and recovery tools

Ventoy Installation

Ventoy creates a multi-boot USB that boots ISO files directly — no need to flash each ISO separately. Drop ISOs onto the USB and Ventoy handles the rest.

Requirements

  • USB stick: 64 GB minimum (128 GB recommended)
  • Linux workstation with ventoy installed
  • All data on the USB will be erased during setup

Installation Steps

Download Ventoy from the official release page. Extract the archive. 
wget https://github.com/ventoy/Ventoy/releases/download/v1.0.99/ventoy-1.0.99-linux.tar.gz
tar xzf ventoy-1.0.99-linux.tar.gz
cd ventoy-1.0.99
Identify the USB device (be absolutely certain — wrong device = data loss). 
lsblk -o NAME,SIZE,MODEL,TRAN | grep usb
Install Ventoy to the USB. This creates two partitions: a large exFAT partition for ISOs and a small EFI partition. 
# Replace /dev/sdX with your USB device
sudo ./Ventoy2Disk.sh -i -r 8192 /dev/sdX

The -r 8192 flag reserves 8 GB at the end for the UPTONX-RECOVERY partition (created next).

Create the UPTONX-RECOVERY partition in the reserved space. 
# Create partition in reserved space
sudo parted /dev/sdX mkpart primary fat32 -- -8192MiB -1MiB
# Format as FAT32 with label
sudo mkfs.vfat -F 32 -n UPTONX-RECOVERY /dev/sdX3
Tip: Ventoy supports Secure Boot If you need Secure Boot support, use sudo ./Ventoy2Disk.sh -i -s /dev/sdX during installation. The UptonX lab hosts use legacy/UEFI boot without Secure Boot, so this is optional.

Recommended ISO Layout

Copy these ISOs to the Ventoy partition (the large exFAT partition, typically /dev/sdX1):

ISO Purpose Size
Ubuntu 24.04 LTS (Desktop Live) Primary recovery OS — SSH, filesystem tools, Docker, networking ~5.7 GB
SystemRescue (latest) Filesystem repair (fsck, xfs_repair), partition management, data recovery ~900 MB
Clonezilla (latest stable) Disk imaging — full-disk backup and restore ~400 MB
Proxmox VE Installer (latest 8.x) Rebuild a Proxmox host from scratch ~1.2 GB
memtest86+ (v7.x) RAM diagnostics — identify bad memory sticks ~10 MB

Recommended Directory Structure on Ventoy Partition

/ventoy/ (Ventoy config — auto-created)
/iso/
├── ubuntu-24.04.2-desktop-amd64.iso
├── systemrescue-11.03-amd64.iso
├── clonezilla-live-3.2.0-5-amd64.iso
├── proxmox-ve_8.3-1.iso
└── memtest86+-7.20.iso
Ventoy auto-detects ISOs Place ISOs anywhere on the Ventoy partition. Using /iso/ keeps things organized. Ventoy will find and list them all in the boot menu regardless of directory structure.

Persistence Partition Setup

The UPTONX-RECOVERY partition (created in step 4 above) stores recovery scripts, credentials, and documentation that persist across boots. This partition is accessible from any booted ISO as a standard FAT32 volume.

Mount the Recovery Partition After Booting an ISO

# Find the UPTONX-RECOVERY partition
lsblk -o NAME,LABEL | grep UPTONX-RECOVERY

# Mount it
sudo mkdir -p /mnt/recovery
sudo mount /dev/sdX3 /mnt/recovery

Keeping ISOs Updated

  1. Download new ISO versions to your workstation
  2. Mount the Ventoy partition: sudo mount /dev/sdX1 /mnt/ventoy
  3. Replace old ISOs in /mnt/ventoy/iso/ with new versions
  4. Unmount: sudo umount /mnt/ventoy
  5. No need to re-install Ventoy — it reads ISOs at boot time
Keep Ventoy itself updated Periodically update Ventoy to support newer ISO formats: sudo ./Ventoy2Disk.sh -u /dev/sdX (preserves data).

proxmox/rejoin-swarm-worker.sh

Re-adds a Proxmox host (or workstation) as a Docker Swarm worker after rebuild or reinstall.

Usage: ./rejoin-swarm-worker.sh <worker-ip>

#!/usr/bin/env bash
set -euo pipefail

# Rejoin a Proxmox host as a Docker Swarm worker after rebuild
WORKER_IP="${1:?Usage: $0 <worker-ip>}"
MANAGER="root@192.168.1.23"

echo "============================================"
echo " Rejoin Swarm Worker: $WORKER_IP"
echo "============================================"

# Determine SSH user
case "$WORKER_IP" in
  192.168.1.95) WORKER_SSH="chris@$WORKER_IP" ;;
  *)            WORKER_SSH="root@$WORKER_IP" ;;
esac

# Step 1: Verify Docker
echo "[1/5] Checking Docker on worker ..."
ssh "$WORKER_SSH" "docker info --format '{{.ServerVersion}}'" || {
  echo "ERROR: Docker not running. Install: curl -fsSL https://get.docker.com | sh"
  exit 1
}

# Step 2: Leave stale swarm
echo "[2/5] Leaving stale swarm ..."
ssh "$WORKER_SSH" "docker swarm leave --force 2>/dev/null || true"

# Step 3: Get worker join token
echo "[3/5] Getting join token ..."
WORKER_TOKEN=$(ssh "$MANAGER" "docker swarm join-token -q worker")

# Step 4: Join swarm
echo "[4/5] Joining swarm ..."
if [ "$WORKER_IP" = "192.168.1.95" ]; then
  ssh "$WORKER_SSH" "sudo docker swarm join --token $WORKER_TOKEN 192.168.1.23:2377"
else
  ssh "$WORKER_SSH" "docker swarm join --token $WORKER_TOKEN 192.168.1.23:2377"
fi

# Step 5: Apply node labels
echo "[5/5] Applying labels ..."
HOSTNAME=$(ssh "$WORKER_SSH" "hostname")
case "$WORKER_IP" in
  192.168.1.74) ssh "$MANAGER" "docker node update --label-add host=msi $HOSTNAME" ;;
  192.168.1.69) ssh "$MANAGER" "docker node update --label-add host=ai $HOSTNAME" ;;
  192.168.1.95) ssh "$MANAGER" "docker node update --label-add host=workstation --label-add gpu=true $HOSTNAME" ;;
esac

echo "Done! Verify: ssh $MANAGER docker node ls"

proxmox/restore-lxc-config.sh

Reapplies the correct AppArmor/nesting configuration to Swarm manager LXC containers (CT 106, 109, 110). Run after any CT config corruption or Proxmox host rebuild.

Usage: ./restore-lxc-config.sh [ctid] — without args fixes all three managers.

#!/usr/bin/env bash
set -euo pipefail

# Required LXC config for Swarm managers:
#   features: keyctl=1,nesting=1
#   lxc.apparmor.profile: unconfined
#   unprivileged: 0

declare -A CT_HOST_MAP=(
  [106]="root@192.168.1.18"   # aux
  [109]="root@192.168.1.77"   # helm
  [110]="root@192.168.1.80"   # aux2
)

fix_ct() {
  local ctid=$1 pve_host=${CT_HOST_MAP[$ctid]}
  echo "Fixing CT $ctid on $pve_host ..."
  ssh "$pve_host" bash -s <<FIXEOF
    CONF="/etc/pve/lxc/${ctid}.conf"
    # Ensure nesting
    grep -q 'nesting=1' "\$CONF" || echo 'features: keyctl=1,nesting=1' >> "\$CONF"
    # Ensure AppArmor unconfined
    grep -q 'lxc.apparmor.profile: unconfined' "\$CONF" || \
      echo 'lxc.apparmor.profile: unconfined' >> "\$CONF"
    # Ensure privileged
    sed -i 's/unprivileged: 1/unprivileged: 0/' "\$CONF"
    grep -E 'features|apparmor|unprivileged' "\$CONF"
FIXEOF
  echo "Restart CT to apply: ssh $pve_host 'pct stop $ctid && pct start $ctid'"
}

if [ $# -eq 1 ]; then fix_ct "$1"
else for ctid in 106 109 110; do fix_ct "$ctid"; done; fi

swarm/redeploy-all.sh

Tears down all Swarm stacks and redeploys them from the repo in the correct order. Run from the repo root or set REPO_DIR.

Usage: ./redeploy-all.sh

#!/usr/bin/env bash
set -euo pipefail
MANAGER="root@192.168.1.23"
REPO_DIR="${REPO_DIR:-$(cd "$(dirname "${BASH_SOURCE[0]}")/../.." && pwd)}"

# 1. Check swarm health
NODE_COUNT=$(ssh "$MANAGER" "docker node ls --format '{{.Status}}' | grep -c Ready")
echo "$NODE_COUNT nodes Ready"

# 2. Remove existing stacks
for stack in $(ssh "$MANAGER" "docker stack ls --format '{{.Name}}'"); do
  ssh "$MANAGER" "docker stack rm $stack"
done
sleep 10

# 3. Ensure overlay networks
ssh "$MANAGER" bash -c 'docker network create --driver overlay --attachable proxy 2>/dev/null || true'
ssh "$MANAGER" bash -c 'docker network create --driver overlay --attachable internal 2>/dev/null || true'

# 4. Sync stack files
rsync -az --delete --exclude='.git' "$REPO_DIR/swarm/" "$MANAGER:/opt/stacks/"

# 5. Deploy in order
for stack in portainer whoami landing uptime-kuma grafana cody; do
  ssh "$MANAGER" "docker stack deploy -c /opt/stacks/$stack/stack.yml $stack" 2>/dev/null || true
  sleep 2
done

# 6. Infisical (needs secrets)
ssh "$MANAGER" "test -f /opt/secrets/swarm.env" && \
  ssh "$MANAGER" "set -a && source /opt/secrets/swarm.env && set +a && \
    docker stack deploy -c /opt/stacks/infisical/stack.yml infisical" || \
  echo "SKIP infisical — /opt/secrets/swarm.env not found"

# 7. Verify
ssh "$MANAGER" "docker stack ls && docker service ls"

Boot & Recovery Scenarios

Symptoms, which ISO to boot, exact steps, and verification
Scenario: Proxmox Host Won't Boot (Filesystem Corruption)

Symptoms

  • Proxmox host stuck at boot, filesystem errors in console output
  • SSH unreachable, web UI at https://<host-ip>:8006 not loading
  • VMs/CTs on that host are down

Boot

SystemRescue ISO — optimized for filesystem repair and data recovery.

Steps

  1. Boot the affected host from the Recovery USB → select SystemRescue
  2. Identify the root filesystem: 
    lsblk -f
# Proxmox typically uses: /dev/sda3 (ext4) or LVM on /dev/pve/root
  3. Run filesystem check: 
    # For ext4:
fsck.ext4 -y /dev/sda3

# For XFS (data drives):
xfs_repair /dev/sdX

# For LVM:
vgscan
vgchange -ay
fsck.ext4 -y /dev/pve/root
  4. If filesystem is unrecoverable:
    • Backup data: mount /dev/sdX /mnt/old && rsync -a /mnt/old/etc/pve/ /mnt/recovery/backup/
    • Reinstall Proxmox using the Proxmox VE ISO from the same USB
    • Restore CT/VM configs from the backup or from PBS (.19)
  5. Reboot and verify Proxmox web UI loads

Verification

  • Proxmox web UI accessible at https://<host-ip>:8006
  • All CTs/VMs on the host are running
  • If Swarm node: verify with docker node ls from manager
Scenario: Docker Swarm Lost Quorum (Majority Managers Down)

Symptoms

  • docker node ls hangs or returns "Error: rpc error: raft quorum lost"
  • Services can't be updated, deployed, or inspected
  • At least 2 of 3 managers are down or unreachable

Boot

No ISO needed — fix from any working machine with SSH access.

Steps

If only 1 manager is down: Fix that manager and quorum restores automatically. Only use force-new-cluster as a last resort when 2+ managers are down.
  1. Find the one surviving manager and force it to become a single-node cluster: 
    # On the surviving manager (e.g., CT 106 at .23):
docker swarm init --force-new-cluster --advertise-addr 192.168.1.23
  2. Rejoin the other managers: 
    MANAGER_TOKEN=$(docker swarm join-token -q manager)
# From each downed manager CT:
docker swarm leave --force
docker swarm join --token $MANAGER_TOKEN 192.168.1.23:2377
  3. If no managers survive, rebuild CT 106: 
    ./docs/scripts/nuke/rebuild-ct106.sh
    Then rejoin all other nodes.

Verification

docker node ls
# All 6 nodes should show Status=Ready
# 3 managers, 3 workers
docker service ls
# All services should show correct replica counts
Scenario: CT 106 (Primary Swarm Manager) Destroyed

Symptoms

  • CT 106 on aux (.18) is destroyed, corrupted, or unrecoverable
  • Traefik can't reach Docker API at tcp://192.168.1.23:2375
  • All *.uptonx.com Swarm services are unreachable (Traefik has no backend)

Boot

No ISO needed — run rebuild script from workstation or another host with SSH access to aux (.18).

Steps

  1. Run the nuke/rebuild script: 
    ./docs/scripts/nuke/rebuild-ct106.sh
  2. Script will output join tokens. Rejoin all other nodes using the tokens printed.
  3. Redeploy stacks: ./docs/scripts/swarm/redeploy-all.sh
  4. Restart Traefik to reconnect to new Docker API: 
    ssh root@192.168.1.15 "cd /opt/traefik && docker compose restart"

Verification

  • docker node ls shows all 6 nodes
  • docker service ls shows all services with correct replicas
  • curl -s https://whoami.uptonx.com returns a response
Scenario: Traefik Down (All *.uptonx.com Unreachable)

Symptoms

  • All *.uptonx.com domains return connection refused or timeout
  • Direct IP access to services still works (e.g., http://192.168.1.18:5000)

Boot

No ISO needed — SSH into CT 102 on aux2 (.80).

Steps

  1. Check CT 102 is running: 
    ssh root@192.168.1.80 "pct status 102"
# If stopped:
ssh root@192.168.1.80 "pct start 102"
  2. SSH into CT 102 and check Traefik: 
    ssh root@192.168.1.15 "cd /opt/traefik && docker compose ps"
# If not running:
ssh root@192.168.1.15 "cd /opt/traefik && docker compose up -d"
  3. Check Traefik can reach the Docker API: 
    ssh root@192.168.1.15 "curl -s http://192.168.1.23:2375/version"
# If this fails, check CT 106 Docker daemon
  4. Check TLS certificates: 
    ssh root@192.168.1.15 "ls -la /opt/traefik/acme.json"
# If missing/empty, Traefik will auto-request via Cloudflare DNS challenge

Verification

curl -s -o /dev/null -w "%{http_code}" https://whoami.uptonx.com
# Should return 200
Scenario: Frigate NVR Crashed (Cameras Offline)

Symptoms

  • Camera feeds not loading in Frigate UI or Home Assistant
  • http://192.168.1.18:5000 not responding
  • No new recordings appearing

Boot

No ISO needed — SSH into aux (.18).

Steps

  1. Run the hardware check first: 
    ./docs/scripts/frigate/check-coral.sh
  2. If containers are down, run emergency restart: 
    ./docs/scripts/frigate/emergency-restart.sh
  3. If Coral TPU is not detected:
    • Physically reseat the Coral USB device
    • Check dmesg | grep apex for driver errors
    • Frigate will fall back to CPU detection (slower but functional)
  4. If NFS archive is stale: ./docs/scripts/network/remount-nfs.sh frigate

Verification

  • Frigate UI loads at http://192.168.1.18:5000
  • All 5 cameras show live feeds
  • Frigate API: curl -s http://192.168.1.18:5000/api/stats
Scenario: NAS Unreachable (NFS Mounts Stale Everywhere)

Symptoms

  • Commands that touch NFS paths hang (ls, df, du)
  • Email RAG VM containers failing to start
  • Frigate NAS archival failing
  • ping 192.168.1.11 fails

Boot

No ISO needed — physical access to NAS required.

Steps

  1. Check physical NAS: Power button, network cable, status LEDs on the UGreen NAS
  2. If NAS is off: Power it on and wait 3-5 minutes for NFSv3 service to start
  3. If NAS is on but unreachable: Check the network switch and cable connections
  4. Once NAS is reachable, remount all NFS shares: 
    ./docs/scripts/network/remount-nfs.sh all
  5. Restart affected services: 
    # Email RAG
ssh chris@192.168.1.110 "cd /opt/email-rag && docker compose restart"

# Frigate (if archival was failing)
ssh root@192.168.1.18 "cd /opt/frigate && docker compose restart"

Verification

ping -c 3 192.168.1.11
ssh chris@192.168.1.110 "ls /mnt/nfs/volumes/email-rag"
ssh root@192.168.1.18 "ls /mnt/nfs/frigate"

Symptoms

  • email-rag.uptonx.com or chat.uptonx.com unreachable
  • VM 401 on ai NUC (.69) won't start or SSH fails to .110

Boot

No ISO needed — access ai NUC Proxmox UI or SSH.

Scenario: Network Misconfiguration (Can't Reach Anything)

Symptoms

  • Multiple hosts unreachable, DNS not resolving
  • Gateway (.1) may or may not be reachable

Boot

Ubuntu 24.04 Live ISO — boot on the workstation for a clean network stack.

Steps

  1. Boot Ubuntu Live from USB on the workstation
  2. Check basic connectivity: 
    # Can we reach the gateway?
ping 192.168.1.1

# Can we reach any Proxmox host?
ping 192.168.1.18  # aux
ping 192.168.1.77  # helm
ping 192.168.1.80  # aux2
  3. If gateway is unreachable:
    • Check physical cable from workstation to switch
    • Check UniFi Cloud Gateway (.1) — power cycle if needed
    • Login: admin / Terry1987!!!
  4. If gateway works but hosts are down:
    • Check TP-Link switch (.13) — VLAN config may be wrong
    • Verify Proxmox hosts are powered on
  5. If DNS is the issue: 
    ./docs/scripts/network/fix-dns.sh
  6. Verify DNS config: 
    # All hosts should use Technitium (.51) as DNS
# If systemd-resolved is pointing elsewhere, fix:
sudo resolvectl dns eth0 192.168.1.51

Verification

ping 192.168.1.1   # gateway
ping 192.168.1.51  # DNS
dig @192.168.1.51 uptonx.com  # should resolve to .15

Cold Boot Sequence

Correct order to bring up UptonX from completely powered off
Order matters! Services have dependencies. Starting things out of order will cause cascading failures. Follow this sequence exactly.

Complete Startup Order

Step Action Wait For Verify
1 Power on NAS (192.168.1.11) 3-5 min for NFS shares to be available ping 192.168.1.11
2 Power on UniFi Gateway (.1) and switches 2-3 min for DHCP and routing ping 192.168.1.1

Physical USB Maintenance

Keeping the recovery USB current and accessible

How to Update ISOs on Ventoy

  1. Plug in the recovery USB on the workstation
  2. Mount the Ventoy partition: 
    sudo mount /dev/sdX1 /mnt/ventoy
  3. Replace old ISOs with new versions in /mnt/ventoy/iso/
  4. Update Ventoy bootloader if needed: 
    cd ~/ventoy-*
sudo ./Ventoy2Disk.sh -u /dev/sdX   # preserves data
  5. Unmount: sudo umount /mnt/ventoy

How to Sync Latest Scripts from Gitea

# Mount the UPTONX-RECOVERY partition
sudo mount /dev/sdX3 /mnt/recovery

# Clone or pull latest from Gitea
cd /tmp
git clone http://192.168.1.58:3000/chris/uptonx-homelab.git
# Or if already cloned:
cd uptonx-homelab && git pull

# Sync scripts to USB
rsync -av --delete docs/scripts/ /mnt/recovery/scripts/

# Copy latest PDF
cp docs/recovery-usb-manual.pdf /mnt/recovery/docs/

# Unmount
sudo umount /mnt/recovery
Automated sync script Create a simple script on the workstation to automate this: 
#!/bin/bash
# sync-recovery-usb.sh
USB_PART=$(lsblk -o NAME,LABEL -nr | grep UPTONX-RECOVERY | awk '{print $1}')
if [ -z "$USB_PART" ]; then echo "USB not found!"; exit 1; fi
sudo mount "/dev/$USB_PART" /mnt/recovery
cd ~/uptonx-homelab && git pull
rsync -av --delete docs/scripts/ /mnt/recovery/scripts/
cp docs/recovery-usb-manual.pdf /mnt/recovery/docs/
sudo umount /mnt/recovery
echo "Sync complete!"

Recommended: Keep Two USB Sticks

  • USB #1: Keep with the homelab rack — immediate access during emergencies
  • USB #2: Keep offsite (office, safe deposit box) — disaster recovery
  • Update both whenever you sync scripts or update ISOs
  • Both should contain identical ISOs and scripts
